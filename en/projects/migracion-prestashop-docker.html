01The problem

The store ran on shared hosting managed with Plesk: limited resources shared with other customers, no control over the PHP version or the server, and nowhere to deploy the in-house tools the company was starting to need (n8n, microservices, ERP).

Every new piece ended up being yet another external service or a patch on top of the hosting.

02The solution

I designed a platform on an Ubuntu 22.04 VPS (12 vCPU, 24 GB of RAM and 720 GB NVMe) where each service lives in its own container and is defined in Docker Compose. Nginx is the single reverse proxy: it routes each domain to its container and terminates TLS with Let's Encrypt certificates that Certbot renews automatically.

I migrated multistore PrestaShop 1.7.8 with its MariaDB database, files and images, keeping PHP 7.4 in a pinned image so modules wouldn't break, and put n8n and the microservices on the same stack with separate internal networks: the database is never exposed to the internet.

03Architecture and flow

  1. InternetHTTPS traffic to the store and the internal tools
  3. NginxReverse proxy, TLS termination and per-domain routing

04Key features

Infrastructure as code

The whole stack is described in docker-compose.yml: bringing up the environment on another machine means cloning, filling in the .env and starting it.

Hands-off TLS

Certificates are issued and renewed automatically with Certbot. Publishing a new subdomain means adding its server block in Nginx and issuing the certificate.

Network isolation

The database is only reachable from the application's internal network; Nginx is the only service that publishes ports.

Pinned versions

PHP 7.4 with the extensions PrestaShop needs (gd, intl, zip, pdo_mysql, opcache) defined in the image.

Persistent data

Product images, modules, themes and MariaDB data live in volumes, independent of the containers' lifecycle.

Running it in production

Basic monitoring, per-container logs and incident handling on the server itself.

05Stack and why

Ubuntu 22.04 LTSStable base with long-term support for the host.
Docker + ComposeReproducible environments, predictable deployments and isolated services.
NginxMature, efficient reverse proxy with fine control over virtual hosts, headers and TLS termination.
MariaDBCompatible with the original dump and performs well on multistore queries.
PrestaShop 1.7.8 / PHP 7.4Keeping the version meant we didn't have to migrate modules at the same time as the infrastructure.

06Technical challenges

  1. Multistore and domains

    PrestaShop stores each shop's domains in the database (ps_shop_url and configuration). After importing the dump you have to adjust domains and paths, and rebuild the cache so each shop resolves correctly behind the proxy.

  2. HTTPS behind a reverse proxy

    With Nginx terminating TLS, PrestaShop receives internal HTTP traffic. The X-Forwarded-Proto headers have to be passed along and respected to avoid redirect loops and mixed content.

  3. Cutover with minimal downtime

    Files synced in advance with rsync, DNS TTL lowered ahead of time and, during the cutover window, a final database dump plus the file delta.

  4. Permissions and caches

    Correct ownership (www-data) on var/cache, img, upload and modules, and clearing the Smarty and Symfony caches when switching environments.

07Results

  • Full control of the server: versions, resources, deployments and logs.
  • One platform for the store, the automations and the microservices.
  • HTTPS certificates and per-domain routing with no manual work.
  • Ready to deploy new internal services in minutes.

08Code

docker-compose.yml (excerpt)
services:
  nginx:
    image: nginx:1.26-alpine
    restart: unless-stopped
    ports: ["80:80", "443:443"]    # the only exposed service
    volumes:
      - ./nginx/conf.d:/etc/nginx/conf.d:ro      # one server block per domain
      - /etc/letsencrypt:/etc/letsencrypt:ro     # Certbot certificates
    networks: [proxy]

  prestashop:
    build: ./prestashop            # php:7.4-apache + gd, intl, zip, pdo_mysql, opcache
    restart: unless-stopped
    env_file: .env
    volumes:
      - ./shop:/var/www/html
    networks: [proxy, backend]     # Nginx reaches it through the proxy network

  mariadb:
    image: mariadb:10.6
    restart: unless-stopped
    env_file: .env
    volumes:
      - db_data:/var/lib/mysql
    networks: [backend]            # no published ports

networks:
  proxy:
    name: proxy
  backend:
    internal: true

volumes:
  db_data:

09What I learned

A migration is mostly inventory work: listing the hidden dependencies before moving anything (cron jobs, SMTP email, absolute paths, modules that write to disk, domains stored in the database) avoids most surprises on cutover day.
