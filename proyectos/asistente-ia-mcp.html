01El problema

La información para tomar decisiones estaba en muchos sistemas distintos y cada consulta requería saber dónde mirar, exportar y cruzar datos.

Los asistentes de IA ya eran útiles para redactar o programar, pero no conocían los datos reales de la empresa, así que sus respuestas sobre el negocio eran genéricas.

02La solución

Construí una capa de herramientas que los asistentes de IA pueden usar mediante Model Context Protocol (MCP). Los scripts internos de ventas, margen, almacén y pedidos se exponen como workflows de n8n con entrada validada y salida JSON.

Se combinan con conectores MCP para Amazon SP-API (pedidos, inventario FBA, devoluciones, ofertas y reportes), Odoo (stock, facturas y ventas) y analítica web. El asistente decide qué herramienta usar, con qué parámetros, y responde con cifras reales.

04Funcionalidades clave

Ventas y margen por tienda

Ventas por país, ticket medio, clientes nuevos y margen bruto real por tienda y periodo.

Rotación de almacén

Stock vivo, lento, frío y muerto valorado a coste en cada almacén.

Amazon

Pedidos, inventario FBA, devoluciones, ofertas y reportes de SP-API en los cuatro marketplaces.

ERP

Consultas de stock, facturas abiertas y resúmenes de venta en Odoo.

Histórico de Clarity

La API de Microsoft Clarity solo devuelve los últimos días; un flujo guarda una foto diaria para construir un histórico consultable.

Motor común

Un sub-workflow interno centraliza la autenticación por token y la extracción de datos; cada herramienta solo define sus parámetros.

06Retos técnicos

  1. Herramientas que un LLM use bien

    Cada herramienta tiene una descripción precisa (qué hace, parámetros, unidades y limitaciones), porque es lo que el modelo lee para decidir. Los errores incluyen un ejemplo de llamada correcta para que el asistente se corrija solo.

  2. Parámetros flexibles, datos estrictos

    Se aceptan alias (start/inicio, shop/tienda) y se normalizan tildes y mayúsculas, pero fechas, rangos e ids se validan con mensajes claros.

  3. Seguridad

    Los scripts internos solo aceptan peticiones autenticadas con token desde n8n y el modelo solo accede a consultas acotadas de lectura, nunca a la base de datos.

07Resultados

  • Preguntas de negocio respondidas en segundos con datos reales.
  • Análisis que antes requerían exportaciones manuales, ahora en una conversación.
  • Base reutilizable: cada script interno nuevo se convierte en herramienta en minutos.

08Código

n8n · nodo «Normalizar parámetros»
// Acepta parámetros del webhook (query/body) o de otro workflow.
const src = $input.first().json ?? {};
const q = { ...(src.query ?? {}), ...(src.body ?? {}) };

const pick = (...keys) => {
  for (const k of keys) for (const o of [q, src]) {
    const v = o?.[k];
    if (v !== undefined && v !== null && String(v).trim() !== '') return String(v).trim();
  }
  return null;
};

const shop  = pick('shop', 'id_shop', 'tienda');
const start = pick('start', 'inicio', 'fecha_inicio');
const end   = pick('end', 'fin', 'fecha_fin');

const example = '{"shop": "1", "start": "2026-08-11", "end": "2026-08-17"}';
const isDate = (s) => /^\d{4}-\d{2}-\d{2}$/.test(s ?? '');

if (!/^\d+$/.test(shop ?? '')) throw new Error(`shop debe ser el id numérico de la tienda. Ejemplo: ${example}`);
if (!isDate(start) || !isDate(end)) throw new Error(`start y end deben ir en formato YYYY-MM-DD. Ejemplo: ${example}`);
if (end < start) throw new Error(`Rango invertido: start (${start}) es posterior a end (${end})`);

return [{ json: { shop, start, end } }];

Proyecto interno: el código fuente es privado. Este fragmento está simplificado, sin credenciales ni datos de negocio.

09Lo que aprendí

Al integrar IA en una empresa, el modelo importa menos de lo que parece. Lo que marca la diferencia son las herramientas que le das: contratos claros, descripciones precisas, validación estricta y errores que expliquen cómo corregirse.
